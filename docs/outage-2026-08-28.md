# Dispatch is not serving

> Found 2026-08-28 while testing drop-in ethers/viem compatibility. Every claim below was checked
> by running the command shown, not inferred.

## What is true

The `RPCDataService` contract is live on Arbitrum One and **two providers are registered and
active on-chain**. Not one of their advertised endpoints answers.

| Advertised endpoint | Owner | Result |
|---|---|---|
| `https://rpc.cargopete.com` | `0xb43b2ccc…` | TLS handshake fails, alert 80 (internal error) |
| `https://dispatch-production-5ffc.up.railway.app` | `0x575267ee…` | HTTP 404 `Application not found` |
| `https://dispatch-service-production.up.railway.app` | `0x575267ee…` | HTTP 404 `Application not found` |
| `https://gateway.lodestar-dashboard.com` | (the gateway) | TLS handshake fails, alert 80 |

Endpoints were decoded from the `ServiceStarted` event data on the proxy
`0x7101d5c1a5c89c3647f5118da118e56c023ba0b9`, so this is what the registry actually tells a
consumer to call.

## Why `rpc.cargopete.com` and the gateway fail

Both resolve to `167.235.29.213`. On that box:

- Caddy is up and answering on :80 (308 redirect) and listening on :443.
- `/etc/caddy/Caddyfile` is **9 lines** and contains only `api.studiozemya.com`.
- `/etc/caddy/Caddyfile.bak.1784543162`, written **2026-07-20 10:26**, contains
  `gateway.lodestar-dashboard.com`, `rpc.cargopete.com` and `api.vindicate-app.com`, all proxying
  to `localhost:8080` / `:8089`. The live Caddyfile is dated the same minute.

So on 20 July something rewrote the Caddyfile and dropped three sites. With no matching site,
Caddy has no certificate to present and answers every handshake with alert 80 — which is why the
failure looks like a TLS problem rather than a missing vhost.

**But the proxy is the smaller half.** Nothing is listening on `:8080` or `:8089` either. There is
no dispatch process, no container, no systemd unit and no directory for it anywhere on that host;
the box runs Foghorn and Zemya and nothing else. Restoring the Caddyfile alone would proxy to a
closed port.

The certificates themselves are fine (valid to 19–20 September) and disk and inodes are healthy, so
neither is the cause. A separate stale entry for `pocket.cargopete.com` — a site not in the
Caddyfile, whose key file no longer exists — has been retrying renewal every ten minutes since, and
is the only thing that shows up in the logs. It is noise, not the fault.

## Why nobody noticed

Nothing watches it. The failure mode is the quiet one: the contract stayed live, the registrations
stayed active, `isRegistered()` kept returning true, and every dashboard kept reporting a healthy
service off on-chain state that says nothing about whether an HTTP endpoint answers.

Lodestar's data-services catalogue said **"Live · Production"** with a green badge and invited
readers to try the endpoint in a playground, for 39 days. That has been corrected.

## Resolved: the gateway is retired

**Decided 2026-08-28.** `gateway.lodestar-dashboard.com` will not run again. The Night's Watch
maintains the GIP and the code; operating a gateway is a different business and not one we are in.

This is a retirement, not an outage, and the write-up below should be read as a post-mortem of how
it stayed invisible rather than as a fault report awaiting a fix. Dispatch remains a **reference
implementation open to any operator**: the contract is live on Arbitrum One, the code is
maintained, GRC-005 stands, and `gib onboard` exists so that an operator's first hour is not spent
discovering our mistakes.

**One thing this leaves undone and it is not cosmetic.** Provider `0xb43b2ccc…` is still registered
on-chain advertising `rpc.cargopete.com`, which will now never answer. Every consumer that follows
the registry will be sent to a host that refuses connections, indefinitely. `stopService` for the
affected chains, or `deregister`, would remove a permanent falsehood from the registry for the cost
of one transaction. It needs the provider key.

## Decisions this still needs
2. **The on-chain registration advertises a dead endpoint.** Until something serves, `0xb43b2ccc…`
   is telling every consumer to call a host that refuses connections. Either restore the endpoint
   or `stopService` for the affected chains. Doing nothing is the option that damages the registry.
3. **`api.vindicate-app.com` went down in the same edit** and is unrelated to Dispatch. Someone
   should be told.

## It is not only Dispatch

A sweep of every service the Lodestar catalogue calls "Live · Production" found two more in the
same state, both labelled with a green badge and an invitation to try them:

| Service | Advertised endpoint | Result | Contract |
|---|---|---|---|
| Seahorn | `seahorn.89.167.109.4.sslip.io` | no answer | `0xdDE3F913…` still holds code |
| Camp | `camp.89.167.109.4.sslip.io` | no answer | `0x8ED61266…` still holds code |

Both hostnames resolve to the Helsinki box via sslip.io. That box has **no vhost for either** and no
seahorn or camp process, container, systemd unit or directory; neither exists on the other host
either. As with Dispatch, the contracts are live and the serving endpoints are gone.

The control in that sweep is `nuthatchds.89.167.109.4.sslip.io`, on the same host, which answers
`402 TAP-Receipt header required` — a working paywall, and proof the box and its proxy are fine.

Two further services, **SDSCE** and **WSaaS**, also claim "Live · Production" but advertise no
endpoint at all, so the claim cannot be checked from outside. SDSCE's own README meanwhile says
there is "no hosted provider gateway or oracle yet, so the service is not usable end-to-end until
at least one provider self-onboards", which contradicts the catalogue. Unresolved, and flagged
rather than rewritten, because absence of an endpoint is not evidence of absence of a service.

## The thing to build regardless

An external probe that calls each registered provider's advertised endpoint on a schedule and
alerts when the registry disagrees with reality. Everything we monitor today is on-chain state,
which is exactly the data that stayed green throughout.
